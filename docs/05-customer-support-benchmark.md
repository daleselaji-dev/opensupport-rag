# 客服 RAG Benchmark：如何向面试官和企业解释

## 一句话说法

> 我没有把“模型能生成一句话”当成成功，而是建立了一个版本化的客服 Benchmark：用真实 CFPB 来源定义可引用证据，用固定问题集测检索和排名，再用人工标注测回答是否被证据支持、是否正确拒答，最后用延迟、成本和人工升级结果判断是否适合运营。

这句话的关键是“任务特定、分层、可复现、风险相关”。没有一个脱离业务的通用分数能证明客服 RAG 可以上线。

## 当前项目的 Eval 到底测什么

现在的 V0.2 seed Eval 是早期检索回归集：

- 8 条中英文问题；
- 每条问题绑定 CFPB 官方真实 URL；
- 测 Hit@3、MRR、检索 p95；
- 测唯一投诉数、Manifest 与 Qdrant 点数一致性；
- 对照 Dense 与 Hybrid；
- 不让 Chat LLM 自己给自己打分。

它适合回答：“这次改了 Embedding、BM25 或 RRF 后，检索有没有回归？”

它还不能回答：“这个系统可以直接上线客服吗？”因为回答完整性、安全拒答、PII、成本、人工升级和实际处理结果还没有进入同一套门禁。

## 企业认可的五层标准

### P0：数据与血缘

必须知道每条证据来自哪里、哪个版本、何时抓取、是否重复，以及一次评测到底使用了哪个索引。当前本地镜像批次已接受 200 条投诉，累积索引为 335 点，Manifest/Qdrant 为 `335 vs 335`；50-case Golden Draft 仍需双人复核后才能作为正式 Gate。

结构审计可重复运行：

```powershell
.\.venv\Scripts\python.exe -m scripts.audit_benchmark
```

结果会写入 `evals/customer_support_benchmark_v0.3_review_packet.json`（可提交到仓库）和 `reports/benchmark_review_v0_3.json`（运行时副本）。

### P1：检索质量

用固定、冻结、人工复核的 Golden Set 测：

- Recall@k / Hit@k：正确证据是否进入候选集；
- MRR：正确证据是否靠前；
- nDCG：多个相关证据的排序是否合理；
- 官方来源覆盖率：流程问题是否至少出现官方指导；
- 语言、意图、来源类型切片：中文问英文资料、投诉流程 vs 企业处理流程不能混为一个平均数。

BEIR 的核心思想也是用异构、可复现的检索任务比较系统，而不是只展示一个手工挑选的问题的最好结果。[BEIR 论文](https://arxiv.org/abs/2104.08663)

### P2：回答与引用

对客服答案做人审或校准后的自动评估：

- Citation validity：引用 ID 是否真实存在；
- Citation support：引用内容是否真的支持这句话；
- Completeness：必需事实是否都出现；
- Unsupported-claim rate：是否加入证据没有支持的承诺；
- Answer relevance：是否回答了用户当前意图；
- Refusal correctness：无证据时是否拒答或升级。

不能把 LLM judge 的一个分数当作真值；至少要保留一小部分人工盲评集。

### P3：安全与风险

客服场景必须单独测：

- 退款承诺；
- 违法/违规认定；
- 账户调查结果；
- PII 和卡号泄漏；
- Prompt injection；
- 冲突来源；
- 过时政策；
- 无法回答时是否升级人工。

NIST AI RMF 强调评估要覆盖设计、部署、使用和持续监控，并把终端用户反馈纳入测量，而不是只测离线模型分数。[NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework)

### P4：运营与业务结果

企业会继续追问：

- 检索 p50/p95；
- 首次响应时间；
- 超时率和错误率；
- 每次请求成本；
- 人工升级准确率；
- 一次解决率（FCR）；
- 平均处理时长（AHT）；
- 用户或客服人员是否采纳答案；
- 数据更新后多久进入索引。

这些指标不是 RAG 分数的替代品，而是证明“质量提升是否真的产生业务价值”。

## 本项目的客服 Benchmark 设计

文件：`evals/customer_support_benchmark_v0.2.json`

首批 10 条不只包含“能回答”的问题，而是按客服风险切片（切片允许重叠，不按下表数量相加）：

| Slice | 数量 | 测试内容 |
|---|---:|---|
| 正常流程问答 | 4 | 信用卡争议、账单错误、投诉流程 |
| 中英文跨语种 | 2 | 中文问题检索英文官方资料 |
| 意图消歧 | 2 | 消费者提交投诉 vs 企业响应投诉 |
| 安全拒答 | 3 | 退款承诺、违法认定、超出知识域 |
| 真实案例边界 | 贯穿 | 投诉是消费者主张，不是事实结论 |

每条记录固定保存：

- 用户问题、语言、意图和风险切片；
- 允许的官方来源 URL；
- 必须出现的来源类型；
- 期望动作：`answer` 或 `refuse_or_escalate`；
- 禁止声明：退款承诺、违法认定、账户调查结论等。

核心证据仍来自公开 CFPB 数据；Benchmark 的问题和标签是评测标注，不是伪造的业务事实。

## 建议的企业 Gate

下面是本项目的建议门槛，不是行业法律规定，最终要根据风险和业务校准：

| Gate | 建议门槛 | 当前状态 |
|---|---|---|
| 数据可复现 | 重复 0；Manifest 精确匹配；≥200 唯一投诉 | 未通过 |
| 检索 | ≥50 条人工复核集；Hit@3/MRR/nDCG 分切片报告 | 当前只有 8 条 seed |
| 引用 | 引用存在性 100%；引用支持度和完整性人工抽检 | 已有存在性校验，支持度未完成 |
| 安全 | 高风险拒答/升级 100% 通过回归集 | 未完成 |
| 运行 | 记录 p50/p95、错误率、超时率、成本 | 部分完成 |
| 业务 | 客服采纳率、人工升级准确率、处理时长改善 | 尚未接入真实运营 |

面试时不要说“我们的 RAG 已经生产可用”。更准确的说法是：

> V0.1 已完成本地真实数据链路；V0.2 已建立检索回归和 Dense/Hybrid 消融；当前数据 Gate 和安全/业务 Gate 尚未通过。下一步是扩大人工 Golden Set、完成引用支持度与拒答评测，再决定是否接受 Hybrid。

这比报一个未经校准的“准确率 90%”更接近企业评审方式。
