# 第 1 课：RAG 到底是什么？

本项目中的 RAG 是四个连续动作：

```text
用户问题 → 把问题变成向量 → 从向量数据库找证据 → LLM 根据证据回答
```

## 用本项目里的真实投诉理解它

假设用户输入：

> 我发现信用卡有一笔不认识的消费，联系客服后没有明确结果。

系统不会要求 LLM 只凭训练记忆回答。它会先：

1. 用 Embedding Model 把这段话转成一串数字，这串数字就是**向量**；
2. 在 Qdrant 中寻找数字模式最接近的真实 CFPB 投诉；
3. 把找到的投诉称为**上下文（context）**；
4. 把“问题 + 上下文 + 规则”发给 LLM；
5. LLM 只能基于这些上下文写出辅助回答，并标出 `[C1]`、`[C2]` 引用。

这就是 Retrieval-Augmented Generation：**检索增强生成**。

## 三个组件分别在做什么

| 组件 | 在 V0.1 中的角色 | 一个直观比喻 |
|---|---|---|
| LM Studio 中的 Embedding Model | 把投诉和问题翻译成可比较的“语义坐标” | 把意思放进地图 |
| Qdrant | 保存这些坐标，快速找附近案例 | 案例地图和导航 |
| LM Studio 中的 Chat Model | 阅读找回来的案例，组织成有边界的答案 | 有引用的研究助理 |

## 为什么光有 LLM 不够

LLM 可能知道“未授权交易”这个概念，却不知道 CFPB 某条真实投诉的具体表达、标签、日期或公司回复类别。RAG 把这些外部事实在提问时提供给它，因此答案可以追溯。

## 为什么光有向量检索也不够

向量检索只会说“这几条案例相似”。它不会把多个案例组织成客服能读懂的说明，也不会自然区分“真实案例中发生过的事”和“下一步应收集什么信息”。LLM 负责这个生成和表达环节。

## 你的本课练习

启动项目、导入 200 条真实投诉后：

1. 分别查询“陌生交易扣款”和“被收了意外费用”；
2. 先不要看 LLM 答案，先看系统找回的前三条投诉；
3. 判断它们为什么相似、又有哪些不相似；
4. 再看答案中的 `[C1]`、`[C2]` 是否确实对应证据卡片。

你完成这四步，就不只是“用过 RAG”，而是亲手验证过检索如何限制生成。
